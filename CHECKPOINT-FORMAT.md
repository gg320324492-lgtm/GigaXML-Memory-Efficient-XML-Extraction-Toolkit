# gigaxml checkpoint format

`checkpoint.json`, written beside the parts when `gigaxml extract --checkpoint-every N`
runs. It is what `--resume` reads to decide how far the previous run got.

**Treat this file as untrusted input if it did not come from your own run.** It lives
on disk, it can be edited or replaced, and `--resume` trusts it to decide how many
records to skip and which files to open. Every field below is validated on read;
anything that does not match is refused rather than corrected.

## Versioning

```json
"version": 1
```

| | |
|---|---|
| Type | integer, exactly `1` |
| Required | **Yes.** A manifest without `version` is refused. |
| Today's value | `1` (`CHECKPOINT_VERSION`) |

`version` is checked by type first, then by value: `true` and `1.0` are refused even
though Python considers both equal to `1`.

> **`version` here is not `schema_version` in the run report.** A manifest version and
> a run-report version are two contracts that move at their own pace: this file
> describes one checkpointed run, a run report describes any run. See
> [`RUN-REPORT-FORMAT.md`](RUN-REPORT-FORMAT.md).

## Top-level keys (all seven required)

| Key | Type | Constraint |
|---|---|---|
| `version` | integer | exactly `1` |
| `source` | object | must hold `path` (string), `size` (integer ≥ 0), `sha256` (64 **lowercase** hex digits) |
| `config` | string | 64 **lowercase** hex digits — a hash of the parsed config, not of the config file's bytes |
| `records_consumed` | integer | ≥ 0; the count a resume skips |
| `rejected` | integer | ≥ 0 **and ≤ `records_consumed`** — a run cannot reject more records than it read |
| `parts` | array | of part objects; may be empty |
| `complete` | boolean | JSON `true`/`false`, **never** a string or a number |

### Part objects

| Key | Type | Constraint |
|---|---|---|
| `name` | string | `part-` + at least five digits + `.csv`, `.jsonl` or `.parquet` |
| `rows` | integer | ≥ 0 |

The `name` shape is exactly what the writer produces (`part_name()` pads to five digits
and does not cap there, so `part-100000.parquet` is normal). Anything else — `../`, a
drive letter, an absolute path, an unknown extension — is refused **while the manifest
is being read**, so no path is ever built from it. This is a read-side restriction only:
part names are generated by the writer and never come from a manifest.

## Unknown keys

**Ignored on read.** Keys this build does not recognise do not stop a resume.

That is the opposite of the config's rule, and the two are different on purpose. A
config is something a person writes and must be strict, because a typo there silently
produces wrong data. A manifest is something a *future version of this tool* may write,
and refusing a manifest because it carries a key from after today would make it
impossible to resume a run made by a newer build.

The corollary: unknown keys are not interpreted either. They are carried nowhere —
this build reads the seven keys it knows and ignores the rest.

## Unsupported versions

A `version` other than the integer `1` is refused:

```
the checkpoint at '<path>' cannot be trusted: it declares format version 2, but this
build reads version 1. Nothing was resumed. Delete the checkpoint to start a fresh run.
```

Refused rather than read as version 1: a manifest from a future format would be
misread under today's rules and a resume would act on values whose meaning is not the
one this build assumes.

## Compatibility and upgrade

**There is no migration mechanism today.** This build writes and reads version 1 only.

- A manifest written by this build is read by this build.
- A manifest from a different version is refused, before anything is skipped or opened.
- **No tool exists to rewrite a manifest between versions, and no forward-compatibility
  promise is made.** Neither is planned for version 1; if they come to exist, they will
  be described here.
